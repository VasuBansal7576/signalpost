# Sources, licences, and data handling

This entry uses Brønnøysundregistrene's public entity, annual-account, role, group, subunit and annual-report-history endpoints. The evaluator-supplied frozen registry CSV is the identity anchor when supplied. A missing frozen row never silently falls back to a live identity. Financial values remain attributed to their source entity, statement scope, reporting period and currency. Annual-report links describe document availability, not extracted PDF contents.

Brreg's entity API documentation identifies the Norwegian Licence for Open Government Data (NLOD) 2.0: https://data.brreg.no/enhetsregisteret/api/dokumentasjon/en/index.html . Registry data is attributed through the source URL, retrieval time, source hash and exact excerpt in each envelope. Confirm the terms applicable to each supplied dataset and endpoint in the evaluation environment.

Exa search is used for discovery and its contents API for public page text. Search titles/highlights never become evidence. Search also requests fresh full-page text and extracted outbound links; those preserved page responses can support claims, subject to the same entity checks as Contents. We assume the configured Exa account and evaluation network policy permit the requested public content. Exa access does not independently establish publisher redistribution rights. A URL being public does not authorize bypassing a login, paywall, access control or platform restriction.

The runner does not crawl authenticated social feeds or install scraping browsers. For verified company pages, a bounded HTTPS HTML request recovers navigation/footer profile links omitted by article extraction. It checks robots.txt, pins public DNS addresses, validates TLS, limits redirects to the verified host (including www), and caps responses at 2 MB. Robots failures/disallow and restricted-platform redirects stop the request. It does not follow the social links. Content reads for LinkedIn, Facebook, Instagram and Indeed are blocked pending a separately licensed connector. Search may return candidate URLs. An outbound social-profile URL can be supported by an attributed company page without reading the restricted profile itself. No independent sentiment is inferred from company promotional copy.

Website attribution requires an exact entity match plus one of: its registered domain; a legal organisation number on a matching brand domain; matching legal name, registered street/address and brand domain; or an exact-org directory's outbound website link corroborated by the company's own page. Directories cannot establish that another directory is the company website. Explicit conflicting organisation numbers fail closed. Recruitment sources use a separate employer gate: the exact legal brand plus org number or matching registered/workplace location and employer context. The quoted role/policy must bind to that employer. Expired vacancies are withheld, and a generic careers navigation link is insufficient. Company profiles must be matching account URLs explicitly linked by the attributed company page; parent accounts, personal profiles and sharing URLs are excluded. A linked franchise, parent, group or management domain alone is insufficient. This is a conservative mechanical identity gate, not a guarantee of semantic entailment. Similar names, group statements and incidental mentions still need review.

Each evidence reference records an extraction method (`registry-json/v1`, `exa-text-extractive/v1`, `exa-text-and-links/v2`, `public-html-links/v1`, or `fixture/v1`). Hashes cover the exact preserved response text: serialized JSON for registry payloads, returned text for Exa, augmented with explicitly labelled provider-extracted outbound links when present; exact response HTML for the bounded website fallback. Identity/ownership support is included as bounded exact excerpts, rather than copying a full HTML page into a claim. They do not purport to hash the publisher's original HTML. Model proposals are checked against saved text and their job's source records before publication. A byline alone is not a company event.

Secrets are read from environment variables or ignored local environment files. API keys and Codex credentials are never included in exports or the submission archive. The model uses either the local Codex subscription broker or an evaluator-supplied API key. The local subscription is a development option and is not required for judging.

Runtime SQLite, raw web caches, model traces and account/session state are excluded from the submission. The smoke-test envelopes include bounded evidence excerpts and hashes; they are an operation/quality demonstration and are never used as answers for a new evaluation batch. No public-company lookup table or benchmark-specific answer rules are embedded in the agent.

For a new run-id, registry responses and Exa contents are requested afresh. The contents request uses `maxAgeHours: 0`. Within a job, identical recorded requests replay instead of being billed again; uncertain pending/failed requests are not silently retried. All such caches remain local and are declared in the README.

Own source code and UI are licensed under MIT. Dependencies retain their individual licences; see `package-lock.json` and `submission/dependency-licences.json`. The public sample selector implements the official seeded sampling procedure using Python's standard library. Challenge prose remains attributed to Builderr; third-party data is not relicensed by the project.

The reliable-fallback extension uses NAV's documented public job-vacancy feed under its [API terms](https://arbeidsplassen.nav.no/vilkar-api). The feed excludes Finn ads. It is not the retired public-feed API and does not rely on the website's fuzzy search. Full raw responses can include public recruitment contact details and remain local. A minimal derivative employer index supports analytical, source-scoped counts; personal contacts, employer descriptions and ad-body text are excluded from that portable index. Explicitly inactive/expired ads do not support current hiring. Cursor updates and removals are applied before a refreshed catalogue is queried.

A nav-feed-index-query/v1 evidence span is a labelled code-derived query receipt. Its hash covers that receipt, not a publisher statement of absence. The verifier checks the catalogue hash, recomputes its employer/subunit query and retains the registry identity/mapping evidence. The separate full-index audit compares records with raw API responses. Such source-scoped zero counts never imply no vacancies elsewhere or cover ads without usable employer IDs.

Specific trusted company-directory records can support actual matching social-account links after exact-org/name/street/location checks. Those evidence sources stay external. The website ownership fallback can corroborate exact legal name and registered locality with the same business phone on an exact-org trusted directory record, without fuzzy matching a misspelled street. See [reliable fallbacks](RELIABLE_FALLBACKS.md).

The optional Exa keyless MCP transport uses the officially documented public server without an API key or sign-in. Only advertised advanced-search and page-fetch tools are called, with request pacing and per-job limits. Search requests set maxAgeHours=0; fetch freshness remains the provider default. MCP receipt text is preserved privately, evidence identifies the extraction method, and results pass the same exact-entity gates as API responses. See https://exa.ai/docs/get-started/exa-mcp . Free keyless access is rate-limited; no unlimited or production-price claim is made.
